# HL-TC-0031 — Promocja zachowuje kolejność DEV → PRE-PROD → PROD

| Pole | Wartość |
|---|---|
| Typ | Ręczny przypadek testowy; nie zgłoszony incydent |
| Obszar | Wydanie |
| Priorytet | P0 |
| Stan definicji | READY |
| Wynik ręczny | **NOT RUN — nie wykonano** |
| Powiązane zmiany | [HL-CHG-0604](../../tracking/changes/HL-CHG-0604.md), [HL-CHG-0605](../../tracking/changes/HL-CHG-0605.md), [HL-CHG-0934](../../tracking/changes/HL-CHG-0934.md) |
| Środowisko | Odczyt dowodów wydania; bez jakichkolwiek mutacji GCP, domen, danych lub PROD. |
| Wersja odniesienia | Nowy cel 0.10.1.0; faktyczne źródło i wynik PRE-PROD odczytaj w rejestrze środowisk. |

## Dane i warunki

Odczyt publicznego/udostępnionego workflow oraz artefaktów. Wybierz źródło i własny przebieg CI najnowszej promocji z [rejestru środowisk](../../ENVIRONMENT-STATUS.md); nie przenoś wyniku ze starszego SHA. Historyczny PRE-PROD 0.9.1.2 miał źródło `3be1f9d2094f1432acacbb782eed1665fd00e6e1`, CI 41233382228 i promocję 41233737873. Nie uruchamiaj nowego wdrożenia ani PROD w ramach tego przypadku.

Brak przygotowanego, odizolowanego fixture lub brak dostępu do wskazanego trybu oznacza BLOCKED, a nie PASS.

Konta `admin1`–`admin3` nie są jednorazowymi fixture. Zgoda na osobny reset po promocji nie jest zgodą na dowolne resetowanie, manipulację zegarem lub podmianę ich danych podczas testów. Ten przypadek nie uruchamia skryptu resetu właściciela.

## Kroki i oczekiwane wyniki

1. **Czynność:** Porównaj SHA źródłowego CI, ręcznej promocji i manifestu publikacji albo potwierdzenia workflow.

   **Oczekiwany wynik:** Zielone CI i promocja dotyczą tego samego pełnego SHA; push sam nie jest promocją GCP. Przy niedostępnym odczycie manifestu zapisujemy ograniczenie dowodu. Zgoda na promocję 0.10.1.0 nie omija odczytu CI; nieudane CI pierwszego podglądu `b1cd650…` nie kwalifikuje tego źródła do wdrożenia.

2. **Czynność:** Sprawdź nazwy obu artefaktów i próbę promocji.

   **Oczekiwany wynik:** Frontend i receipt pochodzą z tej samej udanej próby. Hash ZIP nie jest mylony z hashem tar.gz, manifestu ani digestem obrazu.

3. **Czynność:** Przejrzyj wymagania bramki PROD bez jej uruchamiania.

   **Oczekiwany wynik:** Wymagane są sprawdzone artefakty PRE-PROD; aplikacja nie jest budowana na nowo dla PROD. Sukces DEV tagu nie zastępuje weryfikacji receipt ani konfiguracji kont/API.

4. **Czynność:** Odczytaj dowód trybu API, zgodnych reguł/IAM oraz odbioru zapisu istniejącej wyspy po promocji. Nie wykonuj zmiany ani resetu w ramach tego odczytowego przypadku.

   **Oczekiwany wynik:** Dla bezpośredniego Firestore aktywne reguły przyjmują nowy format także pojedynczej wyspy. Dla API potwierdzono działanie runtime i serwerowego zapisu. Odczytowy test hostingu blokuje wszystkie mutacje, więc jego PASS nie jest dowodem autosave. Osobny odbiór ma pokazać zapis i ponowny odczyt przy zachowaniu historii, bez resetowania kont. Brak dowodu zapisujemy jako niepełny odbiór, a nie domyślny sukces.

## Zakończenie

Zamknij odczyt. Nie usuwaj ani nie nadpisuj artefaktów.

## Raport wykonania

- Tester i data: do uzupełnienia.
- Faktyczny build/SHA oraz środowisko: do uzupełnienia przed startem.
- Wynik: **NOT RUN**; dozwolone po wykonaniu: PASS / FAIL / BLOCKED.
- Dowody: zrzuty ekranu, odpowiedzi/identyfikatory testowych żądań lub log harnessu, bez tokenów i prywatnych payloadów.
- Odchylenia i numer zgłoszonego błędu: do uzupełnienia; incydent powstaje dopiero po zaobserwowanej niezgodności.
