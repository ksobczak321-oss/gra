# Lokalny DEV v32

Uruchomienie: `node scripts/serve-dev.mjs`, domyślnie <http://localhost:3000/harborlight-auth.html>. `PORT` zmienia port; 8000 i 8085 są zarezerwowane. Proces nasłuchuje wyłącznie na loopback. Nie kontaktuje Firebase, Google Cloud ani PRE-PROD i nie korzysta z ADC lub danych dostępowych z chmury.

Lokalne pary login/hasło: **admin1/admin1**, **admin2/admin2**, **admin3/admin3**, zgodnie z poleceniem użytkownika z 15 listopada 2026. Każde konto przyjmuje wyłącznie własne sześcioznakowe hasło; dawne wspólne hasło nie działa. Wskazówka jest widoczna w formularzu i logu startowym. Projekt i klucz sesji to `harborlight-local-dev` i `harborlight-local-dev-auth-v1`. To odrębne konta lokalne, nie reset kont Firebase. Pierwsze wejście tworzy pełny bieżący stan `createState(now,{onboarding:true,ruleset:32})`: 18 osób, Ratusz1, polskie wprowadzenie, nowa żywność. Kolejne wejścia zachowują postęp.

Domyślny plik danych: `/workspace/work/dev-runtime/state-v32.json`; można zmienić przez `DEV_DATA_FILE`. Każda transakcja zapisuje nową pełną kopię do prywatnego pliku tymczasowego i atomowo podmienia docelowy JSON przed zatwierdzeniem w pamięci. Restart zachowuje postęp, społeczność, oferty, wspólne zadania, ograniczenia darowizn i potwierdzenia operacji. Sesje logowania pozostają w pamięci procesu, więc po restarcie trzeba zalogować się ponownie. `DEV_EPHEMERAL=1` uruchamia jawnie nietrwały podgląd; testy korzystają z tego trybu i odrębnych plików tymczasowych. Nie usuwać pliku danych w zwykłym restarcie.

Serwer udostępnia wyłącznie pliki z `PUBLIC_FILES` w `scripts/build_frontend.py`. Dokumentacja, `.git`, kod usług, skrypty, dane kont i plik JSON nie są publiczne. HTML logowania i gry otrzymuje lokalny bootstrap. Adapter wymaga jednocześnie loopback, tego bootstrapu oraz poprawnego handshake `/api/dev/config`; zwykły statyczny localhost zachowuje dotychczasowy tryb. Host i Origin spoza tego samego lokalnego serwera są odrzucane. Tokeny `hl-local.*` są losowymi identyfikatorami sesji sprawdzanymi przez ten proces; nie są tokenami Firebase. Weryfikacja rzeczywistych sesji PROD/PRE-PROD pozostaje bez zmian.

`/healthz`, `/readyz` oraz `/api/v1/config` pokazują rzeczywiste usługi i rodzaj przechowywania: `local-dev-file` lub `server-process-memory`. Prywatny zapis, odczyt i autosave używają istniejącego AccountService i jednej rewizji CAS dla całego archipelagu. Stan gry, jego kopia i kolejka zapisu nie trafiają do localStorage/sessionStorage. Przeglądarka przechowuje wyłącznie metadane sesji i ustawienia języka.

Społeczność, czat dwóch zalogowanych kont, handel PvP i oznaczona symulacja dobroczynności używają istniejących usług transakcyjnych. Handel v32 obejmuje nowe towary, całe monety i nowy pułap cen; zapisane starsze kontrakty zachowują dawną wersję cenową. Wspólny portfel jest zapisywany jako monety matki i `archipelago.sharedWallet`, przy zerowych monetach córek w serializowanych światach. Handel mlekiem zachowuje wiek partii w escrow, dostawie i zwrocie; poza Magazynem licznik centralnego przechowywania nie rośnie.

Kingdom GET/POST `/api/v1/kingdom` wykonuje model Królestwa w jednej transakcji obejmującej wszystkie dotknięte lokalne konta, wspólne zadania i portfele. POST wymaga `action`, `requestId`, `generation`, `expectedRevision`; odpowiedź zawiera `result`, `status`, aktualny `island` i `serverTime`. Potwierdzenia deduplikują ponowienia. Zwykły autosave zachowuje serwerowy sidecar Królestwa. Aktywne wspólne zadanie lub niespłacona pożyczka dla Królestwa blokuje odejście i usunięcie członka sojuszu. Wczytywanie ponownie łączy rekord pożyczki właściciela ze wspólnym zadaniem, aby nie wypłacić nagrody drugi raz.

Darowizny R49: GET/POST `/api/v1/gifts`; POST zawiera `action:{targetId,fromIslandId,toIslandId,cargo}` i takie same metadane CAS. `targetId` to publiczny identyfikator innego członka sojuszu. Ratusz6+, maksymalnie pojemność jednego wspólnego statku, towary ponad rezerwę, raz na konto w24h. Odbiorca nie zatwierdza przyjęcia. Serwer automatycznie dostarcza po10min, zwraca nadmiar po kolejnych10min i pozostawia niedostarczony zwrot na statku do zwolnienia miejsca. Limit24h nie odnawia się po zwrocie. Dziesięciominutowy rejs i zwrot korzystają z dotychczasowego czasu przewozu jako jawnego parametru DEV `DEV_REUSES_EXISTING_CARGO_TIME`. Zegar serwera rozlicza przybycia także bez otwartej przeglądarki odbiorcy; restart odtwarza oczekujące rejsy.

`harborlight-v1-kingdom-client.js` eksportuje `kingdomServiceAction` i `giftServiceAction`, oba z `{cloud,coordinator,getPayload,restore,action=null}`. Helper najpierw zapisuje bieżącą symulację przez CAS, następnie wywołuje API i odświeża zarówno świat, jak i rewizję koordynatora. UI na czas operacji wstrzymuje inne akcje i lokalny tick. Ponowienie niepewnej odpowiedzi zachowuje identyfikator potwierdzenia.

`createDevTimeController(cloud)` z `harborlight-dev-cloud.js` oferuje `status()` oraz `advance(seconds,requestId?)`. `/api/dev/time` sprawdza po stronie serwera uprawnienie wyłącznie admin3, dodatnie całkowite sekundy i powtórzenia żądania. Zwraca `canAdvance`, `offsetSeconds`, `now` oraz `advancedSeconds`; UI przesuwa własną symulację o uzyskaną liczbę sekund i zapisuje CAS. Offset i potwierdzenia są trwałe w lokalnym JSON; ponowione żądanie zwraca `advancedSeconds:0`. Offset musi zostać odczytany przed normalizacją świata po reloadzie, aby przyszły zapisany zegar nie został przycięty do czasu komputera. Zegar wspólnych zobowiązań Królestwa i darowizn pozostaje serwerowym zegarem rzeczywistym, aby admin3 nie przyspieszał terminów innych kont.

Granica autorytatywności: zwykła gospodarka nadal jest symulacją klienta, nie pełnym modelem serwerowym. Królestwo, wspólne wpłaty/wypłaty, handel i darowizny mają własne transakcje. Opaque autosave dowodzi jedynie wydatku netto; pożyczony kapitał jest pomniejszany konserwatywnie o spadek salda, bez zgadywania większego wydatku brutto z operacji o saldzie netto zero. Realni operatorzy płatności, reklamy i przelewy nie są uruchomione.
